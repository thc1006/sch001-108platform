# 問題 02:deadline 日期驗證過於寬鬆

## 一句話

看門狗用 `new Date(comp.deadline)` 判斷日期合法性,這會放行非
`YYYY-MM-DD` 的格式,也會把 `2026-02-30` 這種不存在的日期「正規化」
而非拒絕。

## 留言出處

- PR #22 review comment(Copilot)
- 輪次:第一輪
- 嚴重度:中

## 問題在哪

原本的 `scripts/check-competitions.mjs`:

```js
const deadline = new Date(comp.deadline);
if (Number.isNaN(deadline.getTime())) { /* 報錯 */ }
```

`new Date()` 的解析很寬鬆:

- `new Date('2026/05/19')`、`new Date('May 19 2026')` 都「成功」——格式不符卻過關
- `new Date('2026-5-9')`(未補零)會被當地時間解析而成功
- 時區:ISO 日期字串以 UTC 解析,但 `today` 用本地時間,相減有 ±1 天誤差

## 為什麼是 bug

看門狗的職責就是「抓出資料錯誤」。一個放行格式錯誤、又會把不存在日期
默默改成存在日期的驗證器,等於沒有真正驗證。`deadline` 餵進前端的
`getStatus()` 也會被一致地誤判。

## 修正(commit `222362c`)

改為嚴格三段式驗證:

1. 正則 `/^(\d{4})-(\d{2})-(\d{2})$/` 強制 YYYY-MM-DD 格式
2. 以 `Date.UTC(y, m-1, d)` 建構,再「往返比對」年/月/日——
   `2026-02-30` 會被正規化成 3/2,往返比對 `day` 30≠2 即抓出
3. `today` 與 `deadline` 都化為 UTC 日曆日數值相減,並以台灣時間
   為今天基準,天數差精確且不受 CI 時區影響

## 我有沒有漏掉

Copilot 第一輪抓到。我寫的時候「知道」`new Date` 寬鬆,卻判斷
「資料是自己維護的,應該不會亂填」而選了省事寫法。這是**對驗證工具
放錯了信任假設**——驗證器存在的前提就是「資料可能會錯」。

## 教訓

驗證程式不能假設輸入大致正確,否則它就失去存在意義。日期一律
「格式正則 + 往返比對」,不要單靠 `new Date()`。
