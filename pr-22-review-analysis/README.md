## 誠實的反省:為什麼我沒有自己抓到?

我做過一次「對抗式 self-review」,抓到 **03**,但 **04、05、07 完全漏掉**,
**06 抓到了卻誤判而丟棄**。原因不是「沒看」,而是檢查方式有四個系統性盲點:

### 盲點一:只做「正向追蹤」,沒做「反向追蹤」 → 漏掉 04
我檢查「我寫的程式碼會不會壞」,卻沒問「我**移除**的東西,原本有誰在用?」
PR 把 `const competitionsData = [...]` 從 HTML 拿掉,而 `build-search-index.js`
正是靠正則抓這個陣列來建索引。我把它當成「不在 diff 內、只需確認 Node 24 相容」,
沒有反向問「誰消費了我刪掉的資料形狀」。

### 盲點二:元件各自驗證,沒驗證「跨系統互動」 → 漏掉 05
我分別確認了「腳本的 `fail()` 行為」與「workflow 的 issue 步驟」,但沒把
「腳本 `process.exit(1)`」×「workflow step `if:` 的隱含 `success()` 閘門」
這條**跨檔案互動路徑**走一遍。兩個元件各自正確,接起來卻有洞。

### 盲點三:用「讀」代替「執行」 → 漏掉 07
我把 `build-search-index.js` 讀過、確認沒有危險 API,但沒有真的 `node` 跑一次。
一跑就會看到競賽項目是 28 筆(= 14 × 2),立刻發現重複掃描。
靜態閱讀看不出執行期的數量級錯誤。

### 盲點四:追蹤在「模糊處」就停手 → 06 抓到卻丟棄
我的 review 在「Dropped candidate findings」其實寫了「空字串必填欄位會通過驗證
——因需要規格決策,故丟棄」。我**看到了相鄰的問題**,卻停在「這是規格模糊」就放掉。
Copilot 把它推進一步:值不是字串時 `comp.form.includes()` 會在前端**直接崩潰**
——這就不是規格模糊,是明確的 bug。

### 總結

Copilot 抓到的,剛好全是需要「反向追蹤 / 跨系統 / 實際執行 / 追到底」的問題。
我的對抗式 review 對「diff 內單檔的正向正確性」很紮實,對這四個面向則不足。
這份分析本身,就是把盲點攤開、修正方法論的紀錄。
